# Как объяснить проект преподавателю

## Короткое объяснение своими словами

«Я перенёс текстовую игру Deepspace с BASIC на C. Это бой двух космических кораблей: выбираются система, корабль и вооружение; затем вводятся команды выстрела, манёвра или выхода. Я сохранил формулы и переходы оригинала, включая его странности. Игровая логика отделена от ввода и вывода: в терминале её вызывает C-оболочка, в браузере — JavaScript через WebAssembly. Чтобы проверять перенос, одинаковые ответы подаются оригиналу в Vintage BASIC и моей программе, после чего сравниваются диалоги».

Этот текст — ориентир. Прочитайте код и воспроизведите демонстрацию сами, чтобы отвечать на уточняющие вопросы.

## 1. Оригинал: original/deepspace.bas

BASIC-программа состоит из пронумерованных строк. `PRINT` печатает, `INPUT` ждёт ввод, `IF` выбирает действие, `GOTO` переходит к другой строке. `ON X GOTO ...` выбирает переход по номеру. Переменные с `$` — строки, остальные в этой игре — числа.

Найдите строки 810, 920, 990: ввод системы, корабля, пары «оружие, количество». Строка 1200 получает команду боя. Строка 2760 спрашивает о следующей игре. Числа — адреса шагов программы, не номера строк файла в редакторе.

## 2. Перенос переходов: src/game.c

Функция `ds_advance()` выполняет цикл со `switch(pc)`. `pc` хранит номер следующей BASIC-строки. Каждому `case` соответствует строка оригинала. Присваивание `pc=...` заменяет `GOTO`. Поля структуры `v` сохраняют числовые переменные между вызовами.

На `INPUT` движок останавливается и возвращает тип нужного ответа: 1 — число, 2 — пара чисел, 3 — строка. Оболочка получает ответ, вызывает `ds_numbers()` или `ds_string()`, затем снова `ds_advance()`. Ноль означает конец, минус один — ошибку. Благодаря остановке на вводе браузер не блокируется ожиданием клавиатуры.

`ds_reset()` начинает полный новый сеанс. Внутриигровой ответ YES о повторном бое следует исходным переходам и сохраняет то состояние, которое сохранял BASIC. Это разные действия.

Посмотрите строку `990` в BASIC и `case 990` в C рядом. Затем найдите исходную формулу урона и соответствующий `case` в C. Это нагляднее, чем пытаться выучить весь файл.

## 3. Ввод и вывод: src/cli.c

`main()` запускает движок и повторяет цикл «выполнить до INPUT → прочитать ответ → передать ответ». `fgets()` читает строку, `strtof()` превращает её в число. `host_text()` печатает текст, `host_number()` печатает число, `host_pow()` вызывает `powf()`.

Здесь стандартная библиотека C, без Linux-специфичных окон и терминальных API. Поэтому тот же исходник можно собрать под разные системы. Исполняемый файл macOS нельзя просто запустить на Linux: каждой системе нужен свой результат компиляции.

## 4. Браузер: web/

`web/deepspace.wasm` — скомпилированные `src/game.c` и `src/web_bridge.c`. Это не повторная реализация правил на JavaScript. `engine.mjs` связывает функции C с текстовым выводом и вводом браузера. `app.mjs` обслуживает кнопки, подсказки и сохранение диалога. HTML задаёт элементы страницы, CSS — их вид.

Веб-сервер только отдаёт файлы. Правила игры выполняются локально в браузере. Без загрузки Wasm через HTTP открытый двойным щелчком HTML может не заработать.

## 5. Проверки: tests/

Откройте `tests/dialogues/enemy_destroyed.txt`: это ответы игрока по строкам. Откройте `tests/expected/enemy_destroyed.txt`: это реальный ответ BASIC-интерпретатора. Запустите `make test`, после чего сравните также `build/test-logs/enemy_destroyed.native.txt`.

Скрипт теста передаёт ввод программе автоматически и сравнивает результат. Пробелы и небольшая погрешность печати float допускаются; изменение слов или значимого результата приводит к провалу теста. Для WebAssembly используются те же сценарии и эталоны. Дополнительно `tests/test_browser.mjs` запускает реальный Chromium: проверяет клавиатуру, мышь, эмулированный touch, скачивание диалога и перезапуск. Скриншоты сохранены в evidence/screenshots; один лишь Node.js интерфейс не проверяет.

Если спросят «почему одинаковые бои», объясните `RND(0)` в Vintage BASIC. Если спросят «почему не исправлен фазер», покажите исходный переход: задача была в переносе исходного алгоритма. Подробности и границы совместимости описаны в COMPATIBILITY.md.

## Демонстрация на защите

1. Покажите оригинал, `src/game.c` и соответствие номеров.
2. Выполните `make`, затем `make run`.
3. Пройдите сценарий победы из README, объясняя выбор трюма и команды.
4. Выполните `make test` и откройте один исходный и один полученный лог.
5. Выполните `make serve` и откройте localhost:8000; поясните, что C-ядро то же.
6. Покажите `git log --oneline` и публичный репозиторий после публикации.

На GitHub Actions подтверждён запуск на Windows и Linux 32/64; это можно показать в отчёте evidence/VERIFIED-2026-11-26.md. В собственной JSLinux выполните `sh check-linux-32.sh`: строка pointer_bits=32 и PASS подтверждают запуск 32-битной игры. Не называйте этот проект решением практик 4 и 5.

## Как объяснить дополнительные требования

- Две разрядности: GCC собирает одну программу с `-m32` и `-m64`. Проверяются заголовок ELF и размер указателя внутри запущенной игры. 32-битный процесс работает на 64-битном ядре Linux с поддержкой IA32.
- Три категории: Unix, Windows и Web; macOS и Linux отдельно не считаются.
- Графика: терминальный вывод, современная SVG-схема и программный кадр 320×200 с четырьмя цветами в `web/retro.mjs`. Ретро-режим не означает запуск DOS.
- Ввод: клавиатура или контекстные кнопки, одинаково работающие мышью и касаниями. Touch проверен эмуляцией Chromium, не физическим телефоном.
- Продвинутый тест: `tests/test_core.c` генерирует 2000 последовательностей. Каждая повторяется после постороннего сеанса; хеш вывода и конечных показателей должен совпасть после reset. Всего 6000 сессий. Это фаззинг с проверкой свойств, а не только фиксированные примеры.
